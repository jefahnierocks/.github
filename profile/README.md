# Jefahnierocks

**Independent projects with explicit boundaries.**

Jefahnierocks is the public home for independently governed engineering and
learning projects maintained by
[Jeffrey V. Johnson](https://github.com/verlyn13). It gives experimental work a
clear place to develop while keeping project ownership, maturity, evidence, and
public/private boundaries explicit.

## What this is for

Projects can begin here as focused experiments, utilities, learning systems, or
infrastructure work. The organization provides a common place for ownership and
coordination without absorbing the authority of individual repositories.

Each project repository remains responsible for its own:

- implementation and technical decisions;
- tests, validation, and status of record;
- release and deployment boundaries;
- evidence for public claims;
- license and reuse terms.

The organization coordinates ownership and shared expectations across those
repositories. It does not turn experimental work into product, production, or
client work by implication.

## Selected public projects

### [Host Capability Substrate](https://github.com/jefahnierocks/host-capability-substrate)

A working prototype of a schema-first governance substrate for host-level AI
agents. Its typed ontology models capabilities, authorization, provenance,
policy decisions, and audit evidence explicitly; runtime enforcement remains
intentionally unimplemented.

### [shelltutor](https://github.com/jefahnierocks/shelltutor)

A user-agnostic, single-file Bash course that teaches the shell foundations
needed before `vimtutor`, organized as five mastery-gated stages. It remains
pre-release, and full Linux and macOS walkthrough validation is still pending.

## How governance works today

Governance is currently strongest inside the individual repositories. Projects
use local contracts, status records, tests, decision documentation, and
validation workflows suited to their own maturity and risk.

The shared operating principles are:

- **Repository-local authority:** the closest project contract governs its code
  and evidence.
- **Explicit ownership:** cross-project work names the repository responsible
  for each requested action.
- **Evidence before promotion:** implemented, tested, deployed, and
  production-ready are separate claims.
- **Deliberate visibility:** public and private placement is an explicit
  project decision.
- **Bounded automation:** live infrastructure, credential, and publication
  actions require explicit authorization and a traceable record.
- **Safe refusal:** automation should stop or escalate when authority, evidence,
  or required context is incomplete.

## Conditional governance direction

As concrete needs emerge, Jefahnierocks may adopt organization-level governance
and coordination controls, repository by repository, with an explicit owner and
activation reason. Together, those controls could form a governance and
coordination plane that includes:

- standardized repository contracts and project manifests;
- declared project ownership, maturity, visibility, and data-handling posture;
- organization rulesets, protected branches, and required verification;
- policy-as-code checks for authority, repository boundaries, and publication
  readiness;
- infrastructure-as-code management of approved organization and repository
  settings;
- evidence-preserving CI, drift detection, and auditable handbacks;
- explicit criteria for admitting, promoting, publishing, or operating a
  project.

These are conditional directions, not current organization-wide enforcement.
Each repository remains authoritative for its own implementation, evidence, and
operating boundaries.
